# 代码注释规范（本工程）

> 适用范围：`D:\Desktop\FOC\foc\` 下的所有 `.c` / `.h` 文件。
> 以后新增或修改代码时，注释一律按本文执行。

---

## 0. 每次回答前的自查（自动生效，不需要用户要求）

适用于一切回答，不限于注释问题。**每次发出回答前，按顺序过这五道闸；过不了就改，改不了就删掉那句话。**

### 闸 1：代码行为必须有行号

写下的任何"这段代码它会做 X"，后面必须跟 `文件:行号`。

做不到 → **删掉这句话，或者改成"我没读到，不确定"**。

### 闸 2：不许用推测词打掩护

出现这些词，每一处都必须附行号或实测数据：

```
应该 / 一般 / 通常 / 大概是 / 估计 / 想必 / 按道理
```

附不上 → 换成"不确定"。

### 闸 3：结论之间不许打架

回答里如果有两条最终都落在同一个对象上（例如"X 在中断"和"X 的函数在任务"），
**必须当场说清它们的关系**（是"函数位置"还是"动作位置"，两者的区别在哪）。

说不清 → 只留一条，另一条删掉。

### 闸 4：区分"读过"和"扫过"

只要有一条结论来自我没完整读过的文件，就必须写明读了哪部分。

判据：**我能不能说出这份文件的函数清单和它们的大致篇幅。**

说不出 → 降级为"只看了 X 附近，其余没验证"。

### 闸 5：先写结论，再决定要不要材料

先单独写一句话结论。主答案部分只留那句结论和**不写就会被误解**的关键点。

其余全部删掉 —— 包括行号、源码片段、对比表格。行号只是证据，不是答案。

> 冲突时以闸 1 优先：宁可长，不许没有行号。

### 违反的代价

闸 1 连续三次交不出行号 → 停止讲解参考工程（VESC / rare_foc）的代码，
只做本工程内的事。

## 1. 格式

**统一格式：`空格//空格注释内容`**

```c
// 正确
pwmv2_set_dead_area(PWM, pwm_channel_0, g_dead_ticks);   // 死区
g_pwm_clk_hz = clock_get_frequency(clock_pwm0);          // PWM计数时钟(=AHB)

// 错误
pwmv2_set_dead_area(PWM, pwm_channel_0, g_dead_ticks);   //死区
pwmv2_set_dead_area(PWM, pwm_channel_0, g_dead_ticks);   //  死区
pwmv2_set_dead_area(PWM, pwm_channel_0, g_dead_ticks);   /* 死区 */
```

要点：

- 行内注释：代码后面先留**空格**，再写 `//`，`//` 后面再留**一个空格**
- 独立成行的注释：按当前缩进写 `// 内容`（同上，`//` 后留一个空格）
- 不使用 `/* */` 块注释（唯一例外：文件头版权声明）
- 多行注释拆成多条 `//`，不要用续行的块注释

---

## 2. 简洁

**一条注释只说一件事，一行说完；说不完就说明该写文档而不是写注释。**

| 要求 | 说明 |
|---|---|
| 短 | 尽量不超过 20 个汉字 |
| 只写"干什么" | 不写"为什么""原理""公式推导""注意事项" |
| 不重复代码 | 代码本身能看出来的信息不要写 |
| 不写教程 | 不写背景知识、不写参数取值范围推导 |
| 不用 emoji/符号 | 不用 ⚠ ★ ✅ 之类的装饰符号 |
| 中文 | 用中文，括号用半角 `()`，逗号用半角 `,` |

### 反面例子（以前的写法，太啰嗦）

```c
/* 占空比上限：中心对齐时，下桥导通窗口 = (T - d)/2，必须大于死区
   即 duty_max = 1 - (2×dead + 裕量) / T */
float pwm_get_duty_max(void)

/* 故障时引脚输出 0：高有效驱动下 = 上管关 + 下管关 = 六管全关（电机自由滑行）
   ⚠ 若你的下桥驱动是"低有效"，这里要改成 pwm_fault_output_1，否则会变成下桥全开 */
pwmv2_set_fault_mode(PWM, (pwm_channel_t)ch, pwm_fault_output_0);
```

### 正面例子（现在的写法）

```c
// 占空比上限(受死区限制)
float pwm_get_duty_max(void)

pwmv2_set_fault_mode(PWM, (pwm_channel_t)ch, pwm_fault_output_0);   // 故障时输出0(下桥低有效则改output_1)
```

> 关键提醒仍然可以保留，但压成括号里的一小段，例如上面的 `(下桥低有效则改output_1)`。

## 3. 分节注释

函数内部按"配置阶段"分段，每段一条 `// 标题` 单独成行，段与段之间空一行：

```c
    // 影子寄存器
    pwmv2_set_shadow_val(...);
    ...

    // 比较器绑定:通道N用比较点N*2和N*2+1
    pwmv2_select_cmp_source(...);
```

- 连续做同一件事的多行代码，只在段首写一条注释，**不要每行都写**
- 需要标注"这一行是什么"的时候，用行内注释对齐

---

## 4. 函数注释

- 简单的配置函数**不写**函数头注释
- 需要说明用途的，在函数定义上一行写一条：`// 函数用途`
- 不写 `@param` / `@return` 之类的标签（本工程不用 Doxygen 风格）

```c
// ns转计数周期数(向上取整)
static uint32_t pwm_ns_to_ticks(uint32_t ns)
```

---

## 5. 保留的注释

以下几种必须写，不受"简洁"约束（但仍保持一行）：

1. **单位**：`// 死区(ns)`、`// 周期=(reload+1)个时钟`
2. **硬件相关的坑**：`// 最少2个周期,上限16bit`
3. **待办标记**：`// ADC触发(待加,仍在unlock窗口内)`
4. **被注释掉的代码**：上方写一条 `// 什么情况下打开`

```c
    // 下桥低有效时打开下面三行
    // pwmv2_enable_output_invert(PWM, pwm_channel_1);
```

## 附录：回答问题的规矩（沟通规范）

适用于本项目的一切提问与协助（含 AI 助手）。

1. **只回答被问到的那一件事**，问什么答什么。
2. **不发散**：不补充没被问到的背景、原理、对比、历史、延伸话题。
3. **不给未被要求的建议**：不主动加"下一步建议""顺便提醒""注意事项""要不要我帮你写"。
4. **排版从简**：简单问题不用多级标题、大表格、长清单堆砌。
5. **唯一例外**：不说会导致**硬件损坏、数据错误、编译不过**的，可以额外提醒一句；其余一律不提。
6. 确实需要展开时，**先问一句"要不要展开"**，得到允许再展开。
7. **回答长度与问题匹配**：一句话能答完的，就一句话。

## 附录 B：改代码必须同步更新索引文档

项目索引文档 = `docs/项目描述.md`。

**每次修改代码后，必须同步更新该文档**，逐项检查：

| 检查项 | 对应章节 | 什么时候要改 |
|---|---|---|
| 目录结构 | §4 | 新增 / 删除 / 改名文件，或调整 SES 工程树 |
| PWM 配置表 | §5 | 改了频率、死区、占空比范围、影子值或比较器分配 |
| ADC 配置表 | §6 | 改了通道、触发链、采样参数、数据出口 |
| 开发环境 | §7 | 改了编译方式、工程配置、工具链路径 |
| 遗留问题 | §8 | 发现或解决了一个坑 |
| 当前进度 | §9 | 每完成/新增一项工作 |

配套规则：

1. **新增 `.c` 文件时**，必须同时改 `foc/CMakeLists.txt`（加 `sdk_app_src(...)`），
   否则用 CMake 构建会漏文件、链接报 `undefined reference`。
2. **新增头文件目录 / 新的包含路径时**，同步更新
   `.vscode/c_cpp_properties.json`，否则 VS Code 里会出现红波浪线。
3. 文档改动与代码改动**一起提交**（同一次 `git add` + `git commit`）。

## 附录 C：报告文件内容时的规矩

**凡是声称"文件里有 X"或"文件 A 和文件 B 不一致"，必须把对应原文行贴出来。贴不出来就不许说。**

理由：只读文件不核对，等于拿预期去套内容。要贴原文就会被迫把两处并排看一眼，判断错误在这一步自己就暴露了。

### 要求

1. **贴原文加行号**，不能只给结论：

```
encoder.h:60   extern volatile tEncoder encoder;
foc_cal.c:38   encoder.shadow_count = 0;
```

不写"`foc_cal.c` 里大小写不匹配"这种没有原文的结论。

2. **判断不一致之前，先查一次全部写法。** 认为 A 和 B 不匹配时，
   先用一次搜索把两个符号一起搜出来（如同时搜 `encoder` 和 `Encoder`），
   看定义和用法在同一份输出里长什么样。

3. **"已核对"和"没核对"分开列。** 罗列多条问题时分组标注，
   不允许把推测和已验证混在同一张表里 —— 并排排版会把两者的可信度抹平。

4. **原文只贴能证明结论的那几行**，不复制大段。

### 怎么用这条规矩

我说某处有问题但没贴原文时，回一句"行号"即可。拿不出来就是又在套预期。
