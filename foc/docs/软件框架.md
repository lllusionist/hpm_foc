## 1. 四个执行上下文

一共就四个地方在跑代码。**先看这张表，后面都是它的展开。**

| # | 上下文 | 触发 | 频率 | 干什么 |
|---|---|---|---|---|
| 1 | **快任务** `isr_adc()` | PWM CMP20 → TRGO_0 → TRGM → ADC0 → 内置 DMA 完成 | **40 kHz** | 取三相电流 → 读角度缓存 → Clarke/Park/PI/反Park/SVPWM → 写 PWM 影子 + 过流硬限幅 |
| 2 | **编码器任务** `Encoder_task` | vTaskDelayUntil (半周期×2) | **5 kHz** | MT6835 采集（SPI1+DMA）→ PLL 测速 → 更新 `encoder` 结构体 |
| 3 | **FOC 任务** `Task_FOC` | vTaskDelayUntil(2) @10kHz tick | **5 kHz**（校准/电压每 5 拍 = **1 kHz**）| 状态机 + 保护检测 + 外环（速度/位置）+ 命令超时 |
| 4 | **波形任务** `Vofa_task` | vTaskDelayUntil(1ms) | **1 kHz** | USB CDC 上传波形、配置行、阶跃数据 |
| 5 | **日志任务** `Log_task` | vTaskDelay(2ms) | **~500 Hz** | 把环形缓冲里的字节搬到 UART TX FIFO（非阻塞） |
| — | 纯硬件 | — | — | PWM 生成、死区（FD6288 100 ns）、ADC 触发、DMA 搬运 |

**判据（照抄 VESC）**

| 这件事…… | 放哪 | 为什么 |
|---|---|---|
| 必须和 PWM 严格同步 | **快任务（中断）** | 差一拍就是错的 |
| 可以等、可以睡、晚几百 µs 没事 | **任务** | 中断里等 = 失控 |
| 只在硬件里做的 | **一行代码都不用写** | — |

### 1.1 ★ 最关键的一条：三环不在同一层

| 环 | 在哪 | 频率 | 为什么 |
|---|---|---|---|
| **电流环** | 快任务（中断） | 40 kHz | 要读**刚采的**电流、写**下一拍**的占空比 |
| **速度环** | 控制任务 | 1 kHz | 反馈量本来就是慢任务算的，用 20 kHz 算只是重复劳动 |
| **位置环** | 控制任务 | 1 kHz（可更低） | 机械响应根本跟不上 |

> VESC 的做法一模一样：电流环在 ADC/DMA 中断里，速度和位置环在**同一个线程**里，
> 频率 `sp_pid_loop_rate` 可选 25 Hz ~ 10 kHz（`mcpwm_foc.c:3831` 的 `pid_thread`）。
>
> **三环都塞中断的坏处**：中断被拉长、随时可能超时，而收益是零。

### 1.2 「快任务」≠「裸机」

这里说的"快任务"就是**中断**。它**不是裸机** —— 它和 RTOS 共存、共享 `volatile` 变量、还要发通知。

用"裸机"这个词会误导：真·裸机意味着不能用任何 RTOS API，那它就发不出通知、也就没有故障任务了。

### 1.3 为什么按键/LED 放在控制任务里

按键是「GPIO 读 + 消抖状态机」，LED 是「GPIO 翻转」，**都不阻塞**，而 1 kHz 正好是天然节拍
（每 20 拍扫一次按键就有 20 ms 消抖）。为此单独开一个任务只浪费栈。

将来若 LED 要做 PWM 渐变、按键要做长按/双击动画，再拆成独立任务。

## 2. 任务优先级

`FreeRTOSConfig.h` 里 `configMAX_PRIORITIES = 32`，**数值越大优先级越高**。

| 任务 | 优先级 | 为什么是这个值 |
|---|---|---|
| `Encoder_task` | **20** | 角度晚了电流环就算错，仅次于中断 |
| `Task_FOC` | **15** | 5 kHz 控制环，包含状态机、外环、保护 |
| `Vofa_task` | **5** | 波形上传，纯后台 |
| `Log_task` | **1** | 日志搬运，最低优先级 |
| idle | 0 | — |

> `isr_adc()` **不占 FreeRTOS 优先级** —— 它是硬件中断，比所有任务都硬。
> PLIC 里给它配的是优先级 1，阈值 0（`adc.c` 的 `intc_m_enable_irq_with_priority(ADC_IRQ, 1)`）。

**优先级 = "晚了会怎样"，不是"重要程度"**。故障任务本身不重要，但它要写 Flash（几毫秒）、
不能拖，所以给最高。

**栈和堆要算一下**：4 个任务 × 512 words（2 KB 栈）≈ 8 KB，加上 idle 任务 1 KB + timer 任务 1 KB，
总共约 10 KB，而 `configTOTAL_HEAP_SIZE = 16 KB`。**够，但余量不大** ——
`fault_task` / `comm_task` 用 256 words（1 KB）就够，把省下的留给以后加任务。

## 3. 数据流：谁写、谁读

这是整个框架里**最容易出错**的地方。VESC 的做法是「**每个数据只有一个写者**」。

| 数据 | 写者 | 读者 | 机制 |
|---|---|---|---|
| `FOC.Ia / Ib / Ic / Vbus` | 快任务 | 控制任务、通讯任务 | `volatile` 单字 |
| `FOC.Id / Iq / Vd / Vq` | 快任务 | 控制任务、通讯任务 | `volatile` 单字 |
| `MT6835.elec_angle` | 编码器任务 | **快任务**、控制任务 | `volatile` 单字 |
| `MT6835.elec_speed_lpf` | 编码器任务 | 控制任务 | `volatile` 单字 |
| **发给快任务的设定值**（`mode` + `iq_target`） | 控制任务 | **快任务** | **打包成一个 `volatile uint32_t`**（见 §3.2） |
| 上位机命令（模式/目标/参数） | 通讯任务 | 控制任务 | 队列（任务间，可以阻塞） |
| 波形数据 | 快任务 | 通讯任务 | **环形缓冲**（满了丢，绝不阻塞） |
| 故障码 | 快任务 / 任何任务 | 故障任务 | **任务通知** `xTaskNotifyFromISR` |
| 喂狗计数 | 快任务 | 控制任务 | `volatile` 计数 `++` |

### 3.1 五种传递机制 —— 什么时候用哪个

| 机制 | 语义 | 中断里能用吗 | 什么时候用 |
|---|---|---|---|
| **`volatile` 单字** | 最新值优先，中间的被覆盖 | ✅ 一条 `lw`/`sw` | **默认就用这个**。32 位单字读写天然原子 |
| **打包的 `volatile uint32_t`** | 几个值「一起生效」 | ✅ 一条 `lw`/`sw` | 设定值有多个字段，但能塞进 32 位（见 §3.2） |
| **队列 / 长度 1 的邮箱** | 排队、保序、不能丢 | ⚠️ 只能用 `FromISR` 版，且**不许阻塞** | 任务 ↔ 任务之间；或字段装不进 32 位时 |
| **环形缓冲** | 保序、可丢 | ⚠️ 满了就丢，**绝不阻塞** | 波形/日志这种"流量大、可容忍丢点"的数据 |
| **任务通知 / 事件组** | 立即唤醒，不排队 | ✅ `xTaskNotifyFromISR` | 故障、DMA 完成这种"事件" |

**为什么 `volatile` 单字不用加锁**

32 位机上，读写一个 `float` 就是**一条指令**：

```asm
lw  a5, 0(a0)     # 读: 4 字节一起搬进寄存器
sw  a5, 0(a0)     # 写: 4 字节一起写进内存
```

一条指令**不可能被打断成两半**。所以慢任务正在写、中断同时在读，结果只有"读到旧的"或"读到新的"，
**绝不会读到半新半旧的乱码**。这是硬件保证，不是"大概不会错"。

> ⚠️ **但结构体不是单字**。`volatile struct {...}` 共享给中断是错的 —— 结构体要好几条指令才搬完，
> 搬一半被打断就得到不一致的数据。结构体必须走队列（队列内部有关中断保护）。

### 3.2 ★ 快任务要收两个设定值怎么办

**先纠正一个常见误解：「单字」不是"只能发一个变量"，而是"每个变量单独读写是原子的"。**
两个设定值就用两个 `volatile` 变量 —— 除非它们**必须一起生效**。

**情况 A：两个值互相独立** → 两个 `volatile` 变量，完事。

比如电流模式下的 `id_target` 和 `iq_target`：中断恰好在两句之间读到 `{新 id, 旧 iq}`，
下一拍（50 µs 后）就都是新的了，**没有任何影响**。

**情况 B：两个值必须一起生效** → 四个办法（按推荐度排）

**⭐ 办法 1：打包成一个 32 位字（推荐，零开销）**

只要两个值都能塞进 16 位，就打包进一个 `uint32_t`。一次 `lw` 读完，天然原子。

```c
// 高 8 位 = 模式, 低 16 位 = iq_target (mA)
volatile uint32_t g_cmd_pack;

// ---------- 控制任务：一次性提交 ----------
static inline void cmd_set(uint8_t mode, float iq_a)
{
    int16_t iq_ma = (int16_t)(iq_a * 1000.0f);
    g_cmd_pack = ((uint32_t)mode << 24) | (uint32_t)(uint16_t)iq_ma;   // ★ 一条 sw
}

// ---------- 快任务：一次性读出 ----------
uint32_t cmd = g_cmd_pack;                                             // ★ 一条 lw
uint8_t  mode      = (uint8_t)(cmd >> 24);
float    iq_target = (float)(int16_t)(cmd & 0xFFFFU) * 0.001f;
```

**注意**：用**移位**，不要用 `union` + 位域（字节序/位序是实现定义的）。

**办法 2：长度 1 的邮箱（最通用）**

字段装不进 32 位、或者有浮点/指针时用这个：

```c
typedef struct { uint8_t mode; float id_target; float iq_target; } setpoint_t;
QueueHandle_t g_set_q;                       // xQueueCreate(1, sizeof(setpoint_t))

// 控制任务
setpoint_t sp = { .mode = MODE_CURRENT, .id_target = 0.0f, .iq_target = 5.0f };
xQueueOverwrite(g_set_q, &sp);               // 整组一次换掉

// 快任务
setpoint_t sp;
if (xQueueReceiveFromISR(g_set_q, &sp, NULL) == pdTRUE) {
    g_sp = sp;      // 有新值才更新
}
// NULL = 超时 0 = 绝不阻塞, 中断里必须这么写
```

代价：`xQueueReceiveFromISR` 内部要关中断，约 **1~3 µs**（50 µs 周期的 2~6%）。安全但不是零成本。

**办法 3：双缓冲 + 索引翻转**（零开销，但只允许一个写者，且要 `__sync_synchronize()` fence）
**办法 4：顺序法**（先清零 → 改模式 → 写新目标，只适合"单次切模式"，不适合每毫秒都变的连续量）

> **本工程建议用办法 1**：`{mode, iq_target}` 正好塞进 32 位。以后设定值变复杂了，
> 只改 `cmd_set()` 的实现换成办法 2，接口不用动。

### 3.3 三条规则

1. **不用互斥量传实时数据。** 单字 `volatile` 比锁快，也不会优先级反转。并发安全靠
   "每个数据只有一个写者"**设计出来**，不是靠锁保护出来。
2. **中断里只读任务算好的缓存，绝不做 IO。** `isr_adc` 里读 `MT6835.elec_angle`，
   而不是发起一次 SPI 传输 —— 这就是 VESC 把编码器拆成「线程采集 + 中断读缓存」的原因。
3. **中断里不做浮点除法、`sinf()`、`printf`、`malloc`**（除非确认周期够）。

## 4. 一个 PWM 周期里到底发生了什么

40 kHz → 一个周期 **25 µs**。

```
计数器 = 1
   │
   ├─ CMP20 触发 TRGO_0 → TRGM → ADCx_PTRGI0A
   │     ADC0 注入队列开始转 IA(IN0) → IB(IN1) → IC(IN2)
   │
   ├─ 最后一个通道转完 → ADC 内置 DMA 把结果写进 adc_dma_buf[]
   │     → 拉 IRQn_ADC0
   │
    ├─ isr_adc() 进来 ◄──────── 这里大概还剩 20+ µs 可以随便用
    │     1. 取 Ia / Ib / Ic（从 adc_dma_buf，放在 .noncacheable.bss）
    │     2. 取角度 encoder.phase          ← 只是读个变量，不发起 SPI
   │     3. Clarke  : Ialpha, Ibeta
   │     4. Park    : Id, Iq
   │     5. 电流环 PI : Vd, Vq
   │     6. 反 Park : Valpha, Vbeta
   │     7. SVPWM   : duty_u, duty_v, duty_w
   │     8. 写 PWM 影子寄存器 1~6
   │     9. 喂狗计数（不是真喂，见 §7）
   │
计数器 = reload (5000)
   └─ 周期边界 → 影子值统一生效 → 下一个周期的占空比变了
```

**关键点：影子寄存器在周期边界统一生效**，所以中断里晚一点写也没关系 —— 只要在下一个周期边界前写完。这就是 PWMv2 影子机制的意义。

## 7. 故障通道 + 两条旁路

### 7.1 故障通道：为什么必须单独一条

**故障通道 = 一条「出事了」从"发现的地方"送到"处理的地方"的路。**

因为**发现故障的地方和处理故障的地方，能力完全不同**：

| | 中断（发现） | 任务（处理） |
|---|---|---|
| 时间预算 | 25~50 µs 必须退出 | 可以花几十 ms |
| 能做 | 关断、发通知 | printf、写 Flash、上报、等人按复位 |
| **不能做** | **printf / 写 Flash / 等待 / 分配** | — |

中断发现过流了，但它**没法处理**，只能"喊一声"。

**VESC 实际怎么做的（已核实）**

```
① 发现  mc_interface_mc_timer_isr()  (1 kHz 中断, mc_interface.c:1935)
          if (fabsf(abs_current) > l_abs_current_max)
              mc_interface_fault_stop(FAULT_CODE_ABS_OVER_CURRENT, ..., true /*is_isr*/);

② 喊一声 mc_interface_fault_stop()   (mc_interface.c:1826)
          ★ 它自己不关断! 只做两件事:
             - 故障码存进 m_fault_data
             - chEvtSignalI(fault_stop_tp, 1)      ← 唤醒线程

③ 处理  fault_stop_thread           (mc_interface.c:2850, 优先级 124 = 仅次于内核)
          - 记录故障现场 (电流/电压/占空比/转速) → terminal_add_fault_data()
          - 然后才 mcpwm_foc_stop_pwm()          ← 关断发生在这里 (:2935)
          - m_ignore_iterations = m_fault_stop_time_ms
```

**即：VESC 中断只发通知，关断交给最高优先级线程。**

它敢这样有两个原因：① 线程优先级 124，中断一退出几乎立刻被调度（延迟几十 µs）；
② **它的板子有 DRV 故障引脚**（`IS_DRV_FAULT()`），栅极驱动芯片自己会硬件关断，根本不经过软件。

**★ 但本工程没有过流报警引脚**（`项目描述.md` §9 第 1 条），所以必须自己补一级软件的快关断：

```
第 0 级  电流环自己限流 —— 正常情况根本用不到故障
        PI 的目标值被限幅, 电流上不去

第 1 级  ★ 快任务里最精简的硬限幅（几条指令, 微秒级）—— 本工程必须自己加
        if (fabsf(i_abs) > HARD_LIMIT) {
            pwm_set_duty(0, 0, 0);                                  // 这一拍直接不输出
            xTaskNotifyFromISR(fault_task_h, FAULT_OVERCURRENT,
                               eSetValueWithOverwrite, &woken);
            portYIELD_FROM_ISR(woken);
        }

第 2 级  控制任务里做完整判定（VESC 的 ABS_OVER_CURRENT 就在这层）
        过压/欠压/过温/超速, 用积分判据抗瞬时尖峰, 故障码分类

第 3 级  故障任务: 记故障码 → 写 Flash → 上报上位机 → 刹车 → 等恢复条件
```

**通道用任务通知，不是邮箱** —— 故障不需要排队（只关心最新/最严重的），
需要的是"**立刻**唤醒最高优先级任务"，通知正是干这个的，而且比队列快。

### 7.2 超时刹车（安全网 1）

**输入的"心跳"停了，就主动刹车。**

| 场景 | 没有超时刹车的后果 |
|---|---|
| 上位机程序崩了 / 串口线拔了 | 电机保持 50 A 一路狂奔 |
| CAN 总线断了 | 同上 |
| 遥控器没电了 | 同上 |

**这些情况下控制逻辑完全没问题** —— 它只是在忠实执行"上一条命令"。所以**不能靠控制逻辑来救**。

VESC 的做法（`timeout.c`）：

```c
void timeout_reset(void) {                 // 谁收到有效输入, 谁就调一下
    last_update_time = chVTGetSystemTimeX();
}
// timeout_thread, 10 ms 一轮
if (timeout_msec != 0 && chVTTimeElapsedSinceX(last_update_time) > MS2ST(timeout_msec)) {
    mc_interface_set_brake_current(timeout_brake_current);   // 刹车
}
```

**关键：所有"输入源"都必须喂它。** VESC 里每个 `app_*` 都在调 `timeout_reset()`
（`app_ppm.c:126`、`app_adc.c:483`、`app_nunchuk.c:122`、`app_pas.c:293` ……），默认超时 1000 ms。

**它的思路不是"检查数据对不对"，而是"检查还有没有人在跟我说话"。**

**本工程怎么写**：

```c
// comm_task: 每收到一条完整命令帧
timeout_reset();

// ctrl_task (1 kHz)
if (timeout_secs_since_update() > 0.5f) {     // 500 ms 没收到命令
    cmd_set(MODE_IDLE, 0.0f);                 // 目标清零 + 退出运行
    // 或者更狠: 主动刹车（三相下桥臂全开）
}
```

### 7.3 跨层看门狗（安全网 2）

```
快任务 (20 kHz)  → ++feed_adc;              // 只加个计数
控制任务 (1 kHz) → 检查 feed_adc 有没有涨
                    涨了  → 喂硬件看门狗
                    没涨  → 不喂, 让 MCU 复位
```

这样**中断卡死也能被复位救回来**，不只是任务卡死。
复位原因会记成 `FAULT_CODE_BOOTING_FROM_WATCHDOG_RESET`，事后能查到"上次是卡死重启的"。

### 7.4 超时刹车 ≠ 看门狗（很容易混）

| | 超时刹车 | 看门狗 |
|---|---|---|
| 监控什么 | **输入**还有没有 heartbeat | **程序**还有没有在跑 |
| 发现后做什么 | **刹车**（软件动作，可恢复） | **复位整个 MCU**（硬件动作，重启） |
| 谁来做 | 控制任务 | 硬件 IWDG/WWDG |
| 典型时间 | 500 ms ~ 1 s | 10 ~ 100 ms |

**两个都要有，而且是配合的。**

## 8. 分阶段做（每步都能上板验证）

| 阶段 | 做什么 | 上板看到什么 |
|---|---|---|
| **P1** | `pwm_set_duty()` + 开环旋转：固定电角度斜坡 → SVPWM → 写占空比 | **电机会转**（开环，无力矩控制） |
| **P2** | `foc_adc_midpoint()` 改对 + 电流零点/增益标定 → `FOC.Ia` 变成安培 | 串口打印：电机不转时 Ia≈0A，手堵转时电流会变 |
| **P3** | Clarke/Park/PI/反 Park 接进 `isr_adc()`，用开环角度先闭环电流 | 堵转时电流能被限制住（不再随电压乱涨） |
| **P4** | `enc_task` 拆出来 + 电角度对齐（零位标定）→ 换成编码器角度 | 低速平稳、能正反转 |
| **P5** | `ctrl_task` 状态机 + `fault_task` 保护 + `comm_task` 协议 | 能通过串口调速、过流能停 |

**P1 是最重要的一步** —— 它是唯一能单独确认「PWM 占空比写入 + SVPWM + 硬件驱动」这条链的方式，
不牵扯任何 ADC/编码器/算法。VESC 也有对应的开环测试模式。

## 11. 和 rare_foc 的区别

**先说结论：两者不在同一个维度上，是正交的，应该同时存在。**

- **rare_foc 的状态机管的是「时间维度」**：现在处于哪个阶段 —— `BOOT_UP / IDLE / RUN / CALIBRATION / ANTICOGGING`，一个时刻只有一个。
- **本框架管的是「空间维度」**：这段代码跑在哪个上下文 —— 中断 / 5 kHz 任务 / 1 kHz 任务 / 事件任务，同一时刻好几个在同时跑。

**状态机不该丢，而是应该从 ISR 里搬出来，放进 `ctrl_task`。**

### 11.1 rare_foc 实际长什么样（查证结果）

执行上下文只有 **3 个**：

| 上下文 | 内容 |
|---|---|
| `HAL_ADCEx_InjectedConvCpltCallback()`（`foc.c:216`） | → `MCT_high_frequency_task()` —— **FOC 算法 + 状态机 + 编码器读取 + 过流检查，全挤在这一个中断里** |
| `HAL_TIM_PeriodElapsedCallback(htim4)`（`main.c:236`） | 1 ms，只翻转 `time_base` |
| `main()` 的 `while(1)` | 只有 `vofa_send()` |

频率：`PWM_FREQUENCY = 20000`（`foc.h:14`）、`CURRENT_MEASURE_HZ = PWM_FREQUENCY` → **20 kHz / 50 µs 周期**，和本工程一样。

状态机本体（`mc_task.c`）：`state / state_next / state_next_ready` 三段式 + `MCT_set_state()` 显式转移表 + `enter_state()` / `exit_state()` 钩子。

### 11.2 三个真实问题

**A. 中断里可能走到 `malloc`**

Keil 的静态调用图（`MDK-ARM/Base/Base.htm`）里明确列出这条路径：

```
ADC1_2_IRQHandler ⇒ HAL_ADC_IRQHandler ⇒ HAL_ADCEx_InjectedConvCpltCallback
  ⇒ MCT_high_frequency_task ⇒ exit_state ⇒ CALIBRATION_end
  ⇒ USR_CONFIG_read_cogging_map ⇒ USR_CONFIG_set_default_cogging_map ⇒ malloc
```

即「离开 CALIBRATION 状态的那一次中断」会在中断上下文里分配内存。
（这也和 rare_foc 自己 `AGENTS.md` 的约束 1「无动态内存分配」冲突。）

**B. 编码器 SPI 是无超时的阻塞轮询，而且跑在中断里**

`encoder.c:42-52`：

```c
MT6816_CS_L();
SPI1->DR = data_t[0];
while (!(SPI1->SR & SPI_SR_RXNE));   // ← 没有超时
data_r[0] = SPI1->DR;
MT6816_CS_H();
```

被 `mc_task.c:213` 在**中断里**调用。SPI1 时钟 = 170 MHz / 16 = **10.6 MHz**，两次 16 位传输约 **3 µs**（占 50 µs 的 6%）。

耗时不是主要问题，**主要问题是那个 `while` 没有超时**：编码器一旦不响应（没插、线断、供电掉），
这个中断就**永远出不来** —— FOC 环直接停摆。

**C. 三个任务只实现了一个**

```c
void MCT_high_frequency_task(void);   // 实现了
void MCT_safety_task(void);           // 空函数
void MCT_low_priority_task(void);     // 空函数
```

`Base.map` 里被链接器直接删掉：

```
Removing mc_task.o(i.MCT_low_priority_task), (2 bytes).
Removing mc_task.o(i.MCT_safety_task), (2 bytes).
```

于是过流检查被内联进状态分支（`mc_task.c:228` 和 `:242` 两处几乎一样的代码），
通讯全塞在 `main()` 的 `vofa_send()`。**函数名其实已经想到分层了，只是没真的分到不同执行上下文。**

### 11.3 逐条搬法

| rare_foc 里的位置 | 搬到本框架的哪 |
|---|---|
| `MCT_high_frequency_task()` 里的 `ENCODER_loop()` | → `enc_task`（5 kHz）采集；ISR 只读 `MT6835.elec_angle` |
| 取 `Ia / Ib / Ic`、取 `Vbus` + 滤波 | 留在 ISR（原本就对） |
| `FOC_current()` / `FOC_voltage()`（Clarke/Park/PI/SVPWM/写 CCR） | 留在 ISR（原本就对） |
| 状态切换 + `enter_state` / `exit_state` + `switch(state)` 分发 | → `ctrl_task`（1 kHz） |
| 内联的两处过流检查 | ISR 只留最精简的硬限幅 + `xTaskNotifyFromISR(fault_task)`；完整判定搬 `fault_task` |
| 空的 `MCT_safety_task()` | → `fault_task` 真正实现（过压/欠压/过温/看门狗） |
| 空的 `MCT_low_priority_task()` | → `comm_task` |
| `main()` 里的 `vofa_send()` | → `comm_task` |

### 11.4 状态机里该原样保留的部分

`mc_task.c` 这套设计**写得很好，建议照搬**：

| 保留 | 为什么值钱 |
|---|---|
| `state / state_next / state_next_ready` 三段式 | `state_next_ready` 这个握手让「退出需要时间的状态」能优雅处理 —— 比如 IDLE→RUN 要先给自举电容充电（`mChargeBootCapDelay`），充完才允许切换 |
| `MCT_set_state()` 显式转移表 + 返回码 | `-1 非法转移 / -2 有错误码 / -3 标定无效`，调用方一眼知道为什么被拒 |
| `enter_state()` / `exit_state()` 钩子 | 资源获取/释放成对，不会漏 |
| `StatuswordNew` / `StatuswordOld` 双缓冲 | 改完比一次就知道要不要上报 —— 这是 CiA402 的思路，以后接 EtherCAT 直接用 |

**要改的只有三处：**

1. 转移逻辑从 ISR 搬到 `ctrl_task`
2. `MCT_set_state()` 只能被 `ctrl_task` 调（单一写者）；ISR 想切状态就发 `xTaskNotifyFromISR` 请求
3. `enter_state` / `exit_state` 里不许有耗时操作（尤其 `malloc`）

### 11.5 一句话

> rare_foc 是**一个中断装下所有东西**，再用状态机区分「现在干什么」；
> 本框架是**先把「该在哪跑」分开**，状态机只在 1 kHz 那一层里管「现在处于哪个阶段」。
>
> 状态机解决「什么时候」，分层解决「在哪里」。rare_foc 缺的是后者 —— 而它的状态机本身，值得原样搬过来。
